# 冲动刹车

用户行动力强、想法多，也清楚自己容易在项目中途冲动转向——这个 skill 是他给自己装的刹车。刹车的目的不是拦住他，是让他在踩油门前多看一眼。

## 触发场景

1. **推翻重来**：要重写/推翻/重做现有已能运行的代码
2. **换技术**：要换框架、换库、换语言、大改架构
3. **中途转向**：任务做到一半提出新想法、新需求
4. **想放弃**：项目或模块做到一半说不做了

## 刹车动作

### 推翻重来 → 并行验证
- 现有实现保留在原地，新方案做成独立小原型：分支、feature flag 或单独目录，半天内能跑通
- 两个方案跑同一个真实用例，拿结果对比
- 原型确实更好才迁移，迁移拆成小步提交

### 换技术 → 隔夜决策
- 给一张对比表：各自解决什么问题、迁移成本、主要风险，然后停住，把决定留到下一次会话
- 例外：当前技术有硬伤（跑不通、性能不够、许可证冲突）且证据在手——立即换，不用等
- 决定做出后写入决策日志

### 中途新想法 → 记录后继续
- 把想法追加到 `docs/decision-log.md` 的 Ideas 区，一行：日期、想法、触发原因
- 当前任务继续做完；只有新想法让当前任务彻底失去意义时才中断

### 想放弃 → 最小可用版本
- 先问一句：卡住了，还是腻了？
- 卡住 → 拆小，给出下一个 2 小时内能完成的切片
- 腻了 → 和用户一起定"最小可用版本"边界（最多 3 项），完成它再谈放弃

## 刹车纪律

- 每个冲动只刹一次：给出替代方案和建议；用户听完仍坚持，立刻照办，后续不再重复劝阻
- 语气就事论事，一次说清，不说教
- 大项目默认拆成 1–3 天的短冲刺，每个冲刺收尾时必须有能跑或能演示的东西

## 决策日志

- 位置 `docs/decision-log.md`，项目里没有就创建
- 追加而非覆盖：日期、决定、理由、被否掉的备选
- 决定真正做出时才写，讨论阶段不写
